# gh-activity Specification

Create concise personal work highlights for technical team meetings or compact keyword descriptions for personal time tracking and customer invoicing from GitHub activity, optionally limited to a specific organization. Selection and wording reflect the audience and purpose. Class: workflow-process. Shape: inline-guidance; the bundled executable handles collection, so no additional collection logic or provider-specific mechanics are needed.

Scope: independent activity scope, summary format, and timeframe resolution; read-only collection; evidence-based grouping; copy-ready bullets or comma-separated keywords over daily, weekly, monthly, or custom periods. Excludes whole-team reporting, inferred hours worked, publishing, and changes to GitHub or time-tracking/invoicing artifacts.

Runtime contract: resolve three independent inputs for the current request: scope (all authenticated-user activity or a specific organization), format (meeting bullets or time-tracking/invoicing keywords), and timeframe. Ask for missing inputs together through an available interactive question tool, preserve supplied values, and wait for submitted answers before collecting. An asynchronous tool return or a preselected option is not an answer. Use a direct chat question only when no interactive question tool is available in the current mode. An organization is optional; all-activity scope omits the repository filter. Do not announce or apply format or date defaults, and clarify the actual period when only a cadence is supplied. Resolve requested periods as inclusive UTC dates. Preserve activity status and collection caveats. For meeting highlights, prefer short themes with brief details about implemented features and fixes; omit review/comment-only projects by default, and do not present reviews as authored work. Keyword requests produce one compact comma-separated line of keywords or short noun phrases for the requested period, without full sentences or metadata inside the description; separate daily entries remain supported when requested. Substantive reviews and investigations are eligible in keyword format, including review-only periods. Read SKILL.md and execute scripts/gh-activity.sh at runtime; SOURCES.md records maintenance provenance.

Relevance contract: the format input distinguishes technical meeting updates, personal time tracking, and customer invoicing without adding a fourth input or fixing the timeframe. Meeting details explain substantial changes, technical choices, affected components, and evidenced coordination needs. Personal entries retain identifiable tasks, including smaller fixes, maintenance, reviews, tests, and unfinished investigations. Customer invoice keywords use recognizable technical project/component names and group work into concise descriptions for the requested period. Generic keyword requests require purpose clarification. Preserve actual work and status across audiences; wording must not invent delivery or impact. Validate the same activity set across all three purposes, including small-task, review-only, unfinished, and repeated-daily-work cases.

Presentation contract: each meeting theme has a concise, bold area title on its own unbulleted line, followed by a flat bullet list with a one-line summary first and short bullets elaborating on distinct details. Blank lines separate titles, lists, and topics. Sparse evidence permits fewer details. Meeting highlight text has no embedded Markdown links; useful source URLs appear in plain form after summary/detail text, at the end of the report, or as source bullets after the details. Keep sources brief without duplicate links. Keyword descriptions remain link-free. Validate unbulleted topic titles, flat lists, summary-first ordering, elaboration without repetition, and both appended sources and source bullets against this contract.

Validation: check skill frontmatter and examples against the executable's argument parser; review sparse, partial, draft-only, mixed implementation/review, and review-only activity cases in both formats. Replay the reported bare-invocation failure: no default-period announcement, one interactive call with scope/format/timeframe questions, no final Markdown question list, and no collection before submitted answers. Check each missing-input combination for interactive clarification without collection or defaults, tool-unavailable fallback to a direct chat question, and fully specified requests for immediate collection. Check all-activity scope without `--repo`, organization scope with a quoted glob, explicit answers carried forward during clarification, unresolved cadences, both formats over daily/weekly/monthly periods, separate daily entries, comma-separated noun phrases, and caveats outside the copy-ready description. Trigger examples: “gh-activity”; “Summarize my work in getsentry for last week”; “Prepare GitHub highlights for our weekly meeting”; “Use gh-activity for 2026-W40”; “Give me Clockify keywords for yesterday's GitHub work in getsentry”; “Summarize all my GitHub activity this month as invoicing keywords.” Non-triggers: “Review this PR”; “Fix gh-activity completion”; “Show the whole team's velocity”; “Set up Clockify billing.”

Limitations: authenticated-user scope, inclusive UTC dates, recent-event availability, and contribution lookup limits. No live account query is required to validate skill creation. Revisit the skill when the executable's interface or reporting semantics change. Do not store raw private activity or credentials in skill files.
